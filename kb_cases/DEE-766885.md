## 现象 (Symptom)

- **观察到的问题**：VegaBrightnessController（BC）要迁出 Yocto（NSM-15153）。其 OOY 构建对着 VVRP multimodal（`-mm`）sysroot 里的 picturequality 产物（`pq_client.h` + `libamazonpq_client.so`）编译链接，调用 `PQ_Client::enableAAD(int)`（AAD）与 `PQ_Client::setColorSliderPos(int)`（MWS，色彩滑条）。
- **风险表现**：BC 对 **一个** picturequality SRCREV（sysroot 里的那个）编译链接，而每台设备运行 **各自** 的 SRCREV；`PQ_Client` 是 C++ 类，其 ABI 跨 SRCREV 变化，一旦编译期与运行期版本不一致即 **崩溃**（此前 ACE BT 出过同类事故）。
- **触发条件（与根因分开）**：BC OOY 对 `PQ_Client` 直接 include + link；且设备 SRCREV 与 sysroot SRCREV 的 `PQ_Client` ABI 不一致（尤其 `enableAAD` 的存在性不同）。
- **影响范围**：阻塞用 AAD/MWS 在 Yocto 外构建 BC-{madeleine, electra, waterton, galileo}（NSM-17850），进而阻塞删除 `vega-brightness-controller` 的 Yocto recipe。
- **量化（崩溃率/受阻时长/设备数）**：待确认（票面无量化数据）。

## 排查过程 (Investigation)

> 本票无 bug 实机复现叙述；以下为**方案选型 / 设计决策**路径，真实顺序请本人校订。

1. **证伪「只 bump sysroot SRCREV」**：把 `-mm` sysroot 的 SRCREV 升到含两方法的版本（DEE-763668 / CR-313090490）只治标——任何后续设备层 `picturequality.bbappend` 的 SRCREV 变更都能重新引入 skew。结论：需从「构建期绑定」这一根上解耦。
2. **确认 API 跨版本确实不同**：diff `client/pq_client.h` 各版本 → `dc9bcd8c`（Electra/Madeleine/Miramar/Waterton）**同时有** `enableAAD` 和 `setColorSliderPos`；`3612126c`（Brioche/Galileo）**只有** `setColorSliderPos`、无 `enableAAD`。sysroot 的 base（`74c7482a`）两者都缺（NSM-17849）。【source-diff 验证】
3. **方案选型（票面给了 3 条）**：① 统一 SRCREV（删所有 bbappend 的 override）；② OKIDL 稳定 IPC 接口（消费者完全不链 `libamazonpq_client`）；③ Vodka 产出静态客户端库（客户端代码随消费者而非设备镜像版本化）。
4. **决策演进（需回填票面）**：10/26 评论先定为 **③「新建 Brazil 包 + Vodka 编译的静态客户端」**（附 Chorus doc）。最终 spec（10/30）改为**第 4 条路径：`dlopen` + `extern "C"` shim + Yocto `SRC_URI` 补丁（SRCREV-neutral）**——① 被显式规避、②（OKIDL）降为 Future Plan、③ 未采用。⚠️ JIRA 评论与那份 Chorus doc 反映的是更早的 Vodka 方向，与最终实现不一致，建议更新票面/文档或确认当前口径。【设计决策；偏离票面评论】
5. **为什么 dlopen 方案 ABI-safe**：BC 只解析形如 `int f(void*, int)` / `void* f(void)` 的 **纯 C 函数**；C 函数的二进制形态（调用约定、传参）在每个 build 上一致，不会像 C++ 类 ABI 那样漂移。所有 C++ 细节（`sizeof`、成员布局、vtable 偏移、名字修饰）都留在 `.so` 内，而设备上的 `libamazonpq_client.so` 与该设备的 `amazonpq` daemon **永远同一个 build**，天然自洽。
6. **两侧协作设计**：producer 侧把 `extern "C"` shim 编进 `libamazonpq_client.so.1`（只跨 `int` + 不透明 `void*` 句柄，对象在库内 create/destroy）；consumer 侧 BC 去 include/去 link，改 link `libdl`、运行期 `dlopen`/`dlsym` 绑定设备自带库，用 capability query（`pq_client_supported_features()`）返回的 feature bitmask 决定开关。
7. **跨 SRCREV 可编译**：用 SFINAE/`decltype`（`detect_aad`）编译期探测 `enableAAD(int)` 是否存在，使同一份 shim 源码在缺该方法的 `3612126c` 上也能编译（走只需「能编译」的 `-1` fallback，运行期因 feature bit 为 0 永不触达）。
8. **additive、不惊动既有消费者**：shim 符号以默认可见性导出（库以 `-fvisibility=hidden` 编译），**additive**、不 bump `soversion`，既有消费者 DimmingHal 不受影响。
9. **SRCREV-neutral 交付**：shim 作为 `file://...patch` 进 `VegaMetaVegaRecipesDisplay`(mainline) 的 base recipe `picturequality.bb` 的 `SRC_URI`，`do_patch` 在各产品自己 SRCREV 之上打补丁——**不改任何 bbappend、不改任何源 SRCREV**，只推进 `VegaMetaVegaRecipesDisplay` 包版本。
10. **发布序与 fail-safe**：先铺含 shim 的设备镜像，再放 dlopen BC。任意错序的最坏结果是「PQ 临时 off」（`PqShimNotPresent`），**绝不崩溃**。

**被排除 / 推翻项**：只 bump sysroot SRCREV（治标）；统一 SRCREV（①，侵入所有设备层）；Vodka 静态包（③，评论阶段选过，最终未用）；OKIDL（②，长期方向，暂不做）。

## 根因 (Root Cause)

- **主因**：picturequality SRCREV **不是单点固定**——每个产品在各自 `bbappend` 固定 SRCREV；BC OOY 只对着 `-mm` sysroot 的一个 SRCREV 编译链接，而设备运行各自 SRCREV。`PQ_Client` 为 C++ 类，ABI（对象大小/成员布局/vtable 偏移/名字修饰）跨 SRCREV 变化 → 编译期与运行期版本不一致即崩溃。【source-diff 验证：`dc9bcd8c` 有 `enableAAD`、`3612126c` 无】
- **次因 / 放大**：sysroot 的 base `picturequality.bb` 固定在 `74c7482a`，两方法皆缺（NSM-17849）；仅 bump sysroot SRCREV（DEE-763668）治标不治本。
- **触发条件（与根因分开）**：BC 对 `PQ_Client` 直接 include+link，且运行设备的 `PQ_Client` ABI 与编译所用版本不符（尤以 `enableAAD` 存在性为甚）。

## 解决方法 (Fix)

- **性质**：root-fix（把 BC 对 picturequality 的**构建期依赖彻底移除**，边界降到稳定 C ABI + 运行期绑定）。长期理想是 OKIDL 生成式接口（Future Plan）。
- **producer（picturequality `client/`）**：新增 `pq_client_c.h`（纯 C 接口 + feature-bit 枚举）、`pq_client_c.cpp`（`extern "C"` + `visibility("default")` 导出 `create/destroy/enable_aad/set_color_slider_pos/supported_features`，SFINAE 适配 `enableAAD`，null 句柄返回 `-1`），`client/meson.build` 2 行 additive 改动编进 `libamazonpq_client.so.1`。
- **consumer（BC）**：去 `pq_client.h`、去 link `amazonpq_client`，改 link `${CMAKE_DL_LIBS}`；本地声明 C 签名与 feature-bit；启动时 `dlopen("libamazonpq_client.so.1", RTLD_NOW|RTLD_LOCAL)` 一次并缓存函数指针与 bitmask；两处调用（AAD/色彩滑条）保留在既有 `SUPPORTS_PICTURE_QUALITY/SUPPORTS_AAD/SUPPORTS_MWS` 守卫内，per-call create→call→destroy，非致命；4 个互不重叠 metric（`FailedToLoadPqLibrary` / `PqShimNotPresent` / `PqAadNotSupportedByDevice` / `FailedToUpdateAdaptiveDisplayColorState`）。
- **交付**：SRCREV-neutral 的 `SRC_URI` 补丁进 `VegaMetaVegaRecipesDisplay`(mainline)，不碰 bbappend；发布序「先镜像后 BC」。
- **已完成 + 验证**：
  - producer 符号导出：`readelf --dyn-syms libamazonpq_client.so.1` 见 5 个 `pq_client_*`。【readelf 验证，task 1.6 / 8.2】
  - consumer 解耦：`readelf -d BrightnessController` 的 `NEEDED` 已无 `libamazonpq_client`。【readelf 验证，task 3.2】
  - 功能：Madeleine（`dc9bcd8c`，有 AAD）上 `brightnessctl set AdaptiveDisplayColor 1` → BC 日志 `enableAAD ... result = 0` 且生效。【on-device，task 8.3】
  - 代码主体（shim producer + BC consumer loader/call-site）均已实现（tasks 1.x / 3.x / 4.1 / 5.1 标记完成）。
- **遗留 / open questions**：
  - **交付补丁未落地**（task 7.1 未做：`SRC_URI` patch 尚未进 `VegaMetaVegaRecipesDisplay`）。
  - 降级/发布序 on-device 校验待补：`3612126c`（Brioche）feature-off（8.4）、pre-shim 镜像 `PqShimNotPresent` 不崩溃（8.5）、遵守发布序（8.1）。
  - 可选单测/属性测试（1.4/1.5/1.7/4.2/5.2/5.3）未做。
  - 本 shim 无 CR 记录（待确认）；JIRA 关联的 CR 属 DEE-763668，非本改动。
  - JIRA 状态「Screen」，未关票。

## 影响 (Impact)

- **解除阻塞**：BC 可在**无 picturequality 构建期依赖**下迁出 Yocto 并使用 AAD/MWS（NSM-15153 / NSM-15158 / NSM-17850），进而可删除 `vega-brightness-controller` 的 Yocto recipe。
- **消除一类崩溃**：根除「编译期 vs 运行期 picturequality 版本不一致 → 崩溃」（此前 ACE BT 同类事故）；异构设备版本优雅降级为「feature off」。
- **零回归**：additive 导出 + `soversion` 不变 → 既有消费者 DimmingHal 不受影响；SRCREV-neutral + 不改 bbappend → 回滚/铺开风险低。
- **量化**（受影响设备数、崩溃率、迁移受阻时长、发布门）：待确认（无数据来源）。

## Lessons Learned

> agent 起草，待本人定稿。

- 跨「编译期固定版本 vs 运行期各自版本」的边界，**C++ 类 ABI 是脆的**；把边界降到 C（`int` + 不透明句柄）、让对象只在库内生灭，是消除 ABI skew 的通用手法。
- **运行期 `dlopen` 绑定设备自带库** 比「对着某个 sysroot 版本编译」更贴合「设备各自版本」的现实；配 capability query 做能力协商，异构版本可优雅降级而非崩溃。
- 用 Yocto `SRC_URI` 补丁交付可做到 **SRCREV-neutral、不碰任何 bbappend**，但必须配发布序（先镜像后消费者），并用一个「应恒为 0」的 metric（`PqShimNotPresent`）作为序正确的信号。
- **additive 导出符号 + 不 bump `soversion`** 是不惊动既有消费者的关键。
- 方案会演进（Vodka → dlopen shim）；**定了就回填票面/设计文档**，别让 JIRA 评论与实现脱节。
- 「不支持」与「调用失败」分离：能力由 capability query 唯一裁决，返回码只表 success/运行期失败，避免与 `PQ_Client` 自身负错误码歧义。

- **中文**：为一组 Amazon Echo 智能屏设备消除了亮度控制进程与显示画质客户端库之间的**跨版本 C++ ABI 崩溃风险**——将调用边界下沉为稳定的 C 接口（只传整型与不透明句柄、对象只在库内生灭），消费端改为运行期 `dlopen` 绑定设备自带库并按能力位协商、异构版本优雅降级而非崩溃，并以构建系统补丁做到不改任何设备分支的固定源版本；解除了该进程迁出构建框架的阻塞，且对既有消费者零影响。
- **English**: Removed cross-version C++ ABI crash risk between a brightness-control process and a display picture-quality client library across a family of Amazon Echo smart-display devices by lowering the call boundary to a stable C interface (only ints and an opaque handle cross it; the C++ object lives and dies inside the library) and switching the consumer to bind the device's own library at runtime via `dlopen` with capability-bit negotiation that degrades gracefully instead of crashing — delivered as a build-system patch that changed no device's pinned source revision, unblocking the process's migration out of the build framework with zero impact on existing consumers.
