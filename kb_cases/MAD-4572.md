## 现象 (Symptom)

- 核心现象：用 DRM writeback connector 抓取的图是空的。
- 背景：screenshooter 需要截取 alpha 混合之后的最终合成画面（屏幕录制/投屏，来源 Polus 项目需求），正确做法是走 DRM writeback connector 由显示硬件回写合成结果。默认配置下 Weston 走的是 fallback（renderer screenshooter），log 显示 `Writeback support?[0]: fallback` -> `falling back to renderer screenshooter`。
- 开启 writeback 路径（`/etc/xdg/weston/orpheus.ini` 的 `[Overlays-Core]` 加 `Writeback=true`）后，writeback connector 能走通，但抓出来的图是空的：PNG 只有 4266 字节，1340x800 正常应约 740937 字节。
- 整条链路上没有任何报错：`drmModeAtomicCommit` 返回 0，`screenshooter_done` 正常回调，但图就是空的。

## 排查过程 (Investigation)

> 按本人实际排查路径组织。接手前（2025-06，Yixia Luo 等）已澄清一个前提：writeback 空白不是内核没开 `CONFIG_DRM_WRITEBACK`，驱动的 writeback 是好的（独立程序 `mm_test_writeback` 能抓到图），用户态必须设置 `DRM_CLIENT_CAP_WRITEBACK_CONNECTORS`。本人 2025-09 在 Madeleine 上接手。

1. **复现问题**
   - 在 Madeleine 上开启 writeback 配置，稳定复现：atomic commit 成功、`screenshooter_done` 回调正常，但输出图是空的。

2. **对比 writeback 与 fallback 两种截图方式**
   - fallback（renderer screenshooter）能正常出图，writeback 出空图。
   - 由此确认问题是 writeback 这条路径特有的，而不是 screenshooter 工具本身或通用链路的问题，把范围锁定到 writeback capture 链路。

3. **确定整条 writeback capture 链路的正确性**
   - 逐段验证 writeback 从配置、connector/CRTC 属性设置、atomic commit 到 buffer 回写的每一步，确认链路本身是通的、硬件确实产出了像素数据。
   - 排除内核侧干扰报错：`journalctl -f -p err` 抓到 `dc_hw: error:DC panel0 data underflow`，但跑能正常出图的 `display-writeback` 时同样有这条，判定它不是空图的原因（该问题由 HCG 在 HCGPS-3343 修复）；换 10-08 nightly（Build 1238）后 underflow 消失，又出现 `AXI bus0 error` 和 `arm-smmu-v3 ... EVTQ overflow`，但空图依旧，同样排除。
   - 推翻 AI triage 的误判（2026-03-31）：LEDA 以 HIGH confidence 给出根因是 writeback connector 与 CRTC 不兼容（`crtc=(null)`）。实测链路正常、硬件有数据产出，该结论不成立。
   - 结论：链路和硬件都没问题，问题出在回写 buffer 的「内容」上。

4. **分析 writeback buffer 的像素值，按格式进一步分析**
   - 在 `drm_writeback_save()` 里把回写 buffer 的像素字节 dump 出来，按它的格式 ARGB8888 逐通道解读。
   - 发现该格式带 alpha 通道，而每个像素的 alpha 字节都是 `0x00`，R/G/B 其实有数据——所以整张图被按「全透明」解释，看起来就是空的。
   - 在 Brioche（MT8169）上对照：alpha 非零，不复现。确认这是 SoC 显示控制器回写行为的差异。

## 根因 (Root Cause)

- 主因：Madeleine/Electra 的 writeback 硬件输出 ARGB8888 时不填 alpha 通道，每个像素的 alpha 都是 `0x00`。截图客户端按 ARGB 解释，于是整张图全透明，看起来就是空白。
- 次因：`drm_fb_create_dumb()` 只用 `PROT_WRITE` 做 mmap，CPU 回读 writeback 数据属于未定义行为（本次没有单独验证它对现象的贡献）。
- 触发条件：开启 Writeback 配置，并且平台是 VeriSilicon DC。MTK 平台不触发。
- 验证方式：Madeleine 实机修复后 `screenshooter -r /data/snapshot.png` 正常出图；Brioche 对照不复现。

## 解决方法 (Fix)

- Gerrit 2197172（external/weston, weston10），13 行新增、1 行删除，2026-04-14 合入。Code-Review：asagarw +2，weinon、yixial +1。
  1. `fb.c` / `drm_fb_create_dumb()`：mmap 权限从 `PROT_WRITE` 改成 `PROT_READ | PROT_WRITE`
  2. `drm.c` / `drm_writeback_save()`：pixman 拷贝成功后，对每个像素做 `dst[i] |= 0xFF000000`，把 alpha 强制成不透明。用 `image_copied` 标志保护，未知格式不处理（采纳了 bot review 的建议）
- 性质：在用户态绕过硬件/驱动行为。硬件或驱动能不能自己填 alpha，评审时有人提了问题（asagarw 建议找 Chris Healy、Naresh Sharma 确认是统一到平台代码还是留在用户态），合入时 Gerrit 上还有 2 条评论没有关闭。
- 评审中确认的范围：weston screenshooter 和 gwsi-tool-screenshooter 都走同一条 HW writeback 路径，两边都受益（weinon 确认）。

## 影响 (Impact)

- 打通了 Madeleine/Electra 上基于 HW writeback 截取合成后画面的能力，这是屏幕录制/投屏（Polus 项目需求）的前置条件。
- 截图从 4266 字节的空白图恢复为完整画面（1340x800 时约 740KB）。

## Lessons Learned

> 草稿，需要你根据自己的体会改写

1. 「图看起来是空的」不等于「buffer 是空的」。显示/图像问题先按通道把原始字节值 dump 出来，尤其要看 alpha，不要凭预览图下结论——本例 R/G/B 都有数据，只是 alpha 全 0 被当成全透明。
2. 用「能工作 vs 不能工作」做差分最快收窄范围：先用 writeback/fallback 两种截图方式对比锁定是 writeback 路径特有，再用另一颗 SoC（Brioche）对照坐实是平台行为差异。
3. 同样具备alpha channel的格式还有很多，比如ARGB8888 / ABGR8888 / RGBA8888 / BGRA8888,AYUV,ARGB4444 / RGBA4444
4. 没有alpha channel的格式很多，对应上面的是XRGB8888 / XBGR8888, XYUV8888, 	XRGB4444
5. AI triage 给出 HIGH confidence 也要独立验证。LEDA 的「CRTC 不兼容」结论和实测证据冲突。
6. 跨 SoC 的行为差异（这里是 alpha 通道）在用户态补齐时，要在评审里明确写出「这是 workaround」，并把「平台侧能否统一」作为 open question 跟踪。
