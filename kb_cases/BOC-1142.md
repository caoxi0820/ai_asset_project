## 现象 (Symptom)

- 核心现象：Brioche（MT8169）userdebug/DPK 镜像里默认没有 `modetest`。设备上执行 `modetest` 直接报 `/bin/sh: modetest: not found`，`/usr/bin/modetest` 不存在。
- 影响：`modetest` 是 DRM/KMS 的标准调试工具（枚举 connector / encoder / CRTC / plane，做显示通路验证）。缺它会挡住显示 bring-up、面板/固件/硬件隔离排查，以及依赖该工具的 DTS 自动化流程。
- 严重度不高：Sev3（Inconvenience）。因为可以手动 sideload（从同类 MTK build `adb push` 一个 `modetest` 过去）绕过，所以不是阻塞性问题。
- 票面本身信息极简：description 为空，无附件、无关联票，只有标题 `[Brioche] modetest is not build-in by default`。

## 排查过程 (Investigation)

> ⚠️ 本节是依据 JIRA 变更历史 + 两版 Gerrit 补丁重建的，不是本人口述路径。按模板规则，本人的真实排查/决策叙述应覆盖本节，请据实修订。

1. **定位为「镜像没打包」而非「工具坏了」**
   - 现象是 `command not found`，不是运行报错。对照其余 MTK 平台（Callie/Calypso/Carnival/MT8519）默认带 `modetest`，判断是 Brioche 这块的镜像配方漏了带 `libdrm-tests`（`modetest` 二进制由该子包提供），属平台 bring-up 时的配置缺口。
   - （「其余平台默认带」这条来自 LEDA triage，是旁证，待本人确认。）

2. **最终修复：换到 base layer，用最小 bbappend 根治（挂新票 BOC-1785）**
   - 2026-03-03 合入 Gerrit 2137806（`meta-mediatek-brioche` 这个 base vendor layer，`vendor-drop-4.0`），只有 5 行：新增 `recipes-graphic/drm/libdrm_2.4.125.bbappend`，内容是
     `RDEPENDS:${PN}:append:class-target = " ${PN}-tests"`
     让 `libdrm` 在生成 target 镜像时把 `libdrm-tests`（含 `modetest`）作为运行时依赖带进去。
   - 这版挂在新票 **BOC-1785**（`[Brioche] Build-in libdrm-test into platform image`）下，而不是 BOC-1142。
   - 2026-10-15 本人在 BOC-1142 补了一条评论指向 2137806，说明「the final fix patch is …/2137806」，把本票和真正的修复对上。

3. **推翻 LEDA 自动 triage 的结论**
   - 2026-05 起 LEDA 多次自动 triage（comments 3-6），都断言「根因是 `libdrm-tests` 漏进 `IMAGE_INSTALL`，且修复已在 Gerrit 2024836 合入」。
   - 实际核对 Gerrit：**2024836 是 abandoned，不是 merged**；真正合入的是 base layer 的 2137806，且机制是 `libdrm` 的 `RDEPENDS` 而非直接往 `IMAGE_INSTALL` 塞包。LEDA 把 bot-commit-checker 在 1-08 发到 JIRA 的「补丁已上传」通知误读成了「已合入」。本票标签 `ai-graphics-analysis-medium-accuracy` / `pending-accuracy-graphics-review` 也说明这是中等置信、待人工复核的产物。

## 根因 (Root Cause)

- 主因（已核实）：Brioche 的 libdrm 配方没有把 `libdrm-tests` 声明为 target 镜像的运行时依赖，导致 `modetest` 不随 userdebug/DPK 镜像安装。平台 bring-up 时漏配，不是回归、也不是运行时缺陷。
  - 验证方式：补丁 commit 的 [Test] 为「boot 后检查 `/usr/bin/modetest` 是否存在」。设备侧实际跑过 `modetest -M mediatek` 出表的确认，待本人补。
- 触发条件：仅 Brioche 的 userdebug/DPK 镜像；因为能 sideload 顶替，所以定级 Sev3。
- 需要澄清（待本人）：首版 2024836 为什么选择在 DPK 层并捆绑一堆 VSI libdrm 补丁、又为何放弃，最终为何改到 base layer 并另开 BOC-1785。

## 解决方法 (Fix)

- 最终补丁 Gerrit 2137806（`vendor/mediatek/yocto/echo/meta-mediatek-brioche`，`vendor-drop-4.0`），2026-03-03 合入，挂票 BOC-1785。5 行新增，Code-Review +2（hexren），Verified +1（本人）。
  - 内容：新增 `recipes-graphic/drm/libdrm_2.4.125.bbappend`，`RDEPENDS:${PN}:append:class-target = " ${PN}-tests"`。
  - `:class-target` 的作用是只在生成 target 镜像时生效、不影响 native 构建（评审里 hexren 问了 `class-target` 是干嘛的，本人作了解释）。
  - 性质：root-fix（在正确的 base layer 用最小改动把测试子包作为运行时依赖带进镜像）。
- ⚠️ 唯一的修复补丁是 2137806。Gerrit 2024836（`meta-mediatek-brioche-dpk`）**不是本问题的修复补丁**，它已被 abandoned（2026-02-04），不要把它当成修复。
- 评审遗留：2137806 合入时仍有 1 条 comment 处于 unresolved（即 hexren 关于 `class-target` 的那条讨论线程），已口头解释但未在工具里 resolve。
- BOC-1142 本票的「解决」分两层：关票当时（2026-01-13）接受 sideload 作为权宜；真正的镜像根治通过 BOC-1785 / 2137806 落地。

## 影响 (Impact)

- 让 Brioche userdebug/DPK 镜像默认带上 `modetest`，和其余 MTK 平台对齐，省掉每次排查前手动 sideload 的步骤，打通依赖该工具的显示验证与 DTS 自动化流程。
- 量化影响：改动 5 行（1 个 bbappend 文件）。具体受益的下游流程/测试数量、是否已 cherry-pick 到各出货分支——待确认。

## Lessons Learned

> 草稿，需要你根据自己的体会改写

1. 「把一个工具带进镜像」要落在正确的层、用最小改动：首版在 DPK 层捆绑整份 libdrm recipe + 一堆 VSI 补丁（970 行）被放弃，最终用 base layer 的 5 行 `RDEPENDS:${PN}:append:class-target = " ${PN}-tests"` 根治。Yocto 里让某包随镜像安装，优先考虑把测试子包挂成 `libdrm` 的运行时依赖，并用 `:class-target` 限定只影响 target 构建。
2. 低优先级问题（可 sideload 绕过）容易横跨多个 sprint 拖着；关票时写清楚「当前用什么顶替、真正的 fix 在哪」，并在根治后回填补丁链接到原票（本例 10-15 补链接），能避免后人（和 AI triage）误判修复状态。
3. 对于yocto的架构认识更深一步，早期认知更进一步
