## 现象 (Symptom)

- 工具：`gwsi-benchmark-firstFrameMain`（GWSI 图形 benchmark，测 first frame time）。KPI 目标：Avg ≤ 90ms、Max ≤ 90ms。
- `firstFrameTime` 定义（owning 团队 njjang 澄清）：从 Wayland display 创建到第一个 buffer-present 回调之间的时间，覆盖 surface 创建 → GPU 绘制 → buffer present 整条链路。
- Brioche（MT8169）稳定不达标：
  - 票面首测 Avg 121ms（Max 133、Min 115），`NO(Target<=90.00)`。
  - vtrace 重测（10 次迭代）Avg ≈ 150ms（133–166ms），**每一帧 `isJankyFrame=1`**。
- Galileo（MT8169A）同样不达标：Avg 159.67ms（Max 203）。
- Madeleine（Rubra）作为对照**达标**：Avg 78.67ms（Min 69、Max 92）。
- 复现稳定，非偶发。描述里是「观察到 Brioche/Galileo 跑不到 90ms、Madeleine 能」，本节不下根因结论。

## 排查过程 (Investigation)

> 按本人真实排查路径组织。核心手段是 vtrace/Perfetto 分段对比 + 跨平台对照 + 历史问题佐证。

1. **先确认 benchmark 用途**
   - 怀疑 `firstFrameMain` 是不是 media 专用测量。向 njjang 确认：看 benchmark 源码（`firstFrame.cpp`），它是测 3D/UI 的，不是 media。排除「用错 benchmark」的可能。

2. **跨平台对照，锁定问题范围**
   - 同一 benchmark：Brioche 121ms、Galileo 159ms（都不达标），Madeleine 78ms（达标）。
   - Brioche/Galileo 同属 MediaTek 平台，Madeleine 是另一类 SoC。初步判断差异来自平台/SoC，而非 GWSI 工具本身。

3. **评估并排除 disk IO 为主因（受 PROJVEGA-246906 启发）**
   - PROJVEGA-246906 把同 benchmark 的高延迟归到 disk IO（Mac x86 写速只有 Ubuntu x86 的 1/4）。据此在本平台实测 `dd`：
     - Madeleine 41.7 MB/s，Brioche 36.2 MB/s（另一次测 34 MB/s）。
   - 差距只有 ~13%，远不足以解释 ~60ms（~80%）的延迟差。**结论：disk IO 不是本平台的主因**，不能照搬 PROJVEGA-246906 的「disk IO 主导」。

4. **发现 Dynamic FrameRate（DFR）是贡献因素（MTKPLAT-477）**
   - MT8169 的 DFR：active 60Hz、idle 50Hz，首帧触发 idle→active 切换会增加开销。
   - 实测：关闭 DFR 后首帧延迟从 ~170ms 降到 ~140ms（≈ 30ms）。确认 DFR 是**次要贡献因素**，但不足以补齐全部差距。

5. **发现并排除一个 benchmark 设备误分类（不影响结论）**
   - `firstFrameMain.cpp:55` 硬编码 `width==480 && height==960` 判定为 MM 设备；Brioche 是 480×480，被误判为非 MM、落入 TV regression baseline 分支。
   - 但 `Target Met` 用的是统一阈值 `tAvgFrameTime=90.0`（第 45 行），不随设备类型分支。所以这个 bug 只影响内部回归 baseline，**不影响用户可见的 `NO(Target<=90.00)` 输出**。排除为干扰项。

6. **vtrace/Perfetto 抓 log 做分段对比（关键一步）**
   - 按 wiki《Performance Analysis using VTrace-Perfetto》抓取：host 侧 `python3 cli.py capture_trace --capture-categories graphics --duration 60`，设备侧跑 `gwsi-benchmark-firstFrameMain -f 10`，产出 `graphic_trace.out`（4.2MB，Perfetto 二进制）。
   - **在 Brioche 和 Madeleine 两台都抓**，Perfetto UI 里对齐 `gwsi-benchmark-*` 轨迹比对时间戳。

7. **分段定位：找出三段最耗时的调用（Brioche vs Madeleine）**
   | 阶段 | Brioche | Madeleine | 差值 |
   |---|---|---|---|
   | createOnScreen（surface 创建） | 43ms | 32ms | +11ms |
   | triangle rendering（GPU/EGL 绘制） | **47ms** | **13ms** | **+34ms（3.62×）** |
   | present buffer（提交/present） | 45ms | 30ms | +15ms |
   | 合计（约） | ~135ms | ~75ms | **+60ms / ~80%** |
   - 最大头在 **triangle rendering**，是纯 GPU/EGL 绘制，与 disk IO 无关。本人一度计划优化这一段，但分析清楚后判断这是 SoC 能力限制、用户态难根治。
   - 补充观察：trace 里 vblank 间隔大量落在 ~53ms（≈18.5Hz），与设备在迭代间处于 DFR idle/扩展消隐态一致，佐证 DFR 的贡献。

## 根因 (Root Cause)

- **主因 — SoC 的 GPU 计算能力差距（基于实机 trace 的推断，强）**
  - Brioche/Galileo = **MediaTek MT8169**（GPU 为 **ARM Mali-G52** 级，12nm，Cortex-A53/A55）；Madeleine/Electra = **亚马逊第一方 Rubra SoC**。
  - triangle rendering 阶段 Brioche 比 Madeleine 慢 **3.62×（47 vs 13ms）**，这是 GPU/EGL 绘制，不受 disk IO 影响，是单项最大差距；createOnScreen、present 两段也更慢。合起来说明 MT8169 的图形处理能力（含首个 draw call 的 GPU 提频/冷路径）明显弱于 Rubra。
  - 验证方式：本人在 Brioche/Madeleine 实机抓 vtrace 分段对比（实机）。
  - 旁证：Rubra 的 GPU 当初是「刻意做成比上一代更低功耗、由芯片内硬件 plane 补偿」的设计（Device Performance Summit 2026），即便这样一颗收着的 GPU，冷启动绘制仍优于 MT8169 的 Mali-G52——说明差距是实打实在 SoC 层面。
- **次因 — MTK 显示控制器的 Dynamic Frame Rate（实机验证）**
  - MT8169 的 DFR（MTKPLAT-477）idle 时 50Hz、首帧触发切到 60Hz active，给 createOnScreen/present 增加 idle→active 切换开销。
  - 验证方式：关闭 DFR 实测首帧从 ~170 降到 ~140ms（≈30ms，实机）。
- **排除项**
  - disk IO：Brioche vs Madeleine 仅差 ~13%（36.2 vs 41.7 MB/s），不足以解释 ~60ms 差距，排除为主因（实机测 + 推断，推翻 PROJVEGA-246906 的「disk IO 主导」在本平台的适用性）。
  - benchmark 设备误分类（`firstFrameMain.cpp:55`）：只影响内部 regression baseline，不影响 `Target Met` 判定（统一 90ms），排除。
- **触发条件**：MT8169 平台（Brioche/Galileo）跑 `gwsi-benchmark-firstFrameMain` 冷启动首帧时触发；Rubra 平台（Madeleine）不触发（达标）。
- **待确认**：
  - Rubra GPU 的确切型号/规格（内部未查到公开型号，先记为「亚马逊 1P Rubra SoC 的集成 GPU」）。
  - MT8169（base）上 Mali-G52 的确切配置（MC1 单核 vs MP2 双核）；MT8169A（Galileo）公开资料为 Mali-G52 MP2。
  - triangle render 3.62× 差距中，GPU 提频（governor/OPP 冷启动）与 GPU 算力本身各占多少，未进一步拆分。

## 解决方法 (Fix)

- **未做代码修复**。2026-02-09 以「not top priority to fix」关票（Resolution: 已修复/Resolved，fixVersion: Beta）。
- 上游 Yixia Luo 在 **DEE-349057** 移除了 `gwsi-test-firstFrame` 用例；本人在票里询问 Brioche 侧是否同步移除。
- 性质：**won't-fix**。根因是平台硬件能力（SoC/GPU + 显示控制器 DFR 行为），不是软件缺陷；且该 benchmark KPI 不是 OS OFB 出货门槛（沿用 PROJVEGA-246906 的处置先例）。
- 未实施的缓解方向（候选，均**未验证**，部分来自 LEDA 建议 + 常识，交由本人取舍）：
  1. GPU 预热：进程启动时先跑一个极小的 dummy render，把 GPU 提前提频，降低首个 draw call 的冷路径开销。
  2. 测试侧强制关 DFR（test-only），把显示控制器因素从 KPI 里剥离。
  3. 给 MTK 平台单独设 first-frame KPI 阈值（统一 90ms 对 MT8169 不现实）。

## 影响 (Impact)

- 把「Brioche/Galileo 跑不到 90ms first-frame KPI」从「软件可能有回归」澄清为「SoC/GPU 层面的能力差距」，避免在软件栈里空耗，并为后续 MTK 平台的 KPI 目标设定提供了依据。
- 量化：Brioche 121–150ms vs Madeleine ~78ms（+60ms / ~80%）；三段分解 createOnScreen +11ms、triangle render +34ms（3.62×）、present +15ms；DFR 可量化贡献 ~30ms；disk IO 差距仅 ~13%。
- 这套 vtrace 分段 + 跨平台对照的证据链，后来也成为 LEDA 自动 triage 给出「no action、符合 PROJVEGA-246906 先例」结论的依据。
- 待确认：是否据此为 MTK 平台调整了 first-frame KPI；上面的缓解方向是否有人跟进。

## Lessons Learned

> 草稿，按你自己的体会定稿。

1. **性能问题要用 trace 分段量化，别只盯总延迟。** 把 150ms 的总延迟用 vtrace/Perfetto 拆成 createOnScreen / triangle render / present 三段，才看得出 GPU 绘制（3.62×）是最大头、disk IO 不是主因。有分段数据的结论比「感觉是芯片慢」有说服力得多——这也是说服 owning 团队和让 triage 认账的关键。
2. **跨平台对照是定位硬件性能问题最快的收窄手段。** 同一 benchmark 在 Brioche/Galileo（MT8169）和 Madeleine（Rubra）上一比，立刻把问题从「软件慢」收窄到「SoC 能力差距」，并能把 disk IO、DFR、benchmark bug 等因素逐个量化剥离。
3. **历史问题要用来做横向佐证，但结论必须在本平台重新验证。** PROJVEGA-246906（同 benchmark、disk IO 影响论、KPI 非 OFB 目标的 won't-fix 先例）和 MTKPLAT-477（DFR 机制）都是好线索；但 PROJVEGA-246906 的「disk IO 主导」在本平台实测只差 13%，直接被推翻。照搬历史结论是陷阱。
4. **分清主因 / 次因 / 干扰项。** GPU 绘制差距是主因，DFR 是可量化的次因（~30ms），disk IO 和 benchmark 误分类是干扰项。多因素叠加的性能问题，混为一谈就会得出错误权重。
5. **不是所有 benchmark 失败都要/能修。** 当根因是硬件能力、且该 KPI 非出货门槛时，记录清楚根因与证据链后 won't-fix 是合理处置——但要留下可复用的分析，别只写一句「not top priority」关票（否则后人和 AI triage 都得重查一遍）。
