## 现象 (Symptom)

- 工具：`gwsi-test-vsync`，测的是 **vsync 信号到达的间隔**（不是显示面板 FPS）。期望每帧间隔 ≈ 16667µs（60Hz），抖动在容差内即 `gwsi-test-vsync passed`。
- Brioche、Galileo、Madeleine 上**均可复现失败**（跑 100/500/1000 帧都失败），说明这是**跨设备一致的线程调度行为**，并非某颗 SoC 特有。（票面早期一条评论曾记为 Madeleine 通过，经本人进一步测试 Madeleine 同样复现。）
- 失败机理：绝大多数间隔在 ~16650–16700µs，但偶发尖峰明显超容差（如 16885µs、19566µs），VTrace 实测到有一次 vsync gap 高达 **23ms**（远超 16.67ms），导致判定失败。
- 复现环境：`displaymanager-debug window_secure_mode disable` 后 `gwsi-test-vsync -disable-ev -f 100`。
- 本节只记录「观察到什么」，不下根因结论。

## 排查过程 (Investigation)

> 按本人真实排查路径组织，票面评论与 Gerrit 补丁作为佐证。前期一度被带偏到「显示面板 FPS/PLL 调校」方向，后文有澄清。

1. **先排除显示链路/面板 FPS（推翻被带偏的方向）**
   - 初始怀疑是 vblank 间隔异常（Weinong：16885 > 16667）。随后 MTK 侧沿「面板 FPS」深挖：示波器量 MIPI 波形、调 PLL_CLK（232/235/236MHz，找最接近 60Hz 的值，235MHz=60.12Hz）、查 SSC。
   - 本人澄清（关键）：baker Liu 用示波器量的是**显示面板的输出帧率**，而本 issue 测的是 **VSYNC 信号到达**，两者不是一回事。把排查方向从「面板/PLL 调校」拉回到「vsync 信号与软件链路」。

2. **跨设备对照，判断是否平台特有**
   - 同一测试在 Brioche/Galileo/Madeleine 上**都复现失败**（早期一度以为 Madeleine 通过，复测后确认同样失败）。多设备表现一致，说明根因是**跨设备共通的系统/调度行为**，而不是某台设备或 GWSI 工具本身的缺陷。

3. **排除 DFR（与 BOC-1215 不同，这里 DFR 不是因）**
   - MTK（Yongqiang Niu）给了「默认关 DFR」补丁 1980058，本人用 dry-run 镜像实测**无改善**，排除 DFR。

4. **modetest 验证内核/驱动层 vsync 正常（排查关键点 1）**
   - 先 `systemctl stop weston@graphic` 关掉 weston service，再 `modetest -s 33:#0 -v` 直接走内核 DRM/KMS 做 vsynced page flip。
   - 结果 freq 稳定在 ~59–60Hz、**通过**。说明 **kernel/驱动层的 vsync 本身没问题**，问题在用户态。

5. **VTrace 定位到「等待超时」**
   - VTrace 抓到一次 vsync 间隔 23ms。GWSI 里该间隔由 `DisplayUpdateHandler.cpp` 的等待逻辑控制（client 侧 condition_variable 定时等待）；debug 日志显示 `timeOutInMicroSecs=16293`（本应等 ~16ms），**实际等了 23ms**。
   - 当时三个假设：① CPU 调度占用过多导致延迟；② 代码计算不准；③ 其他。

6. **提高线程优先级验证是调度问题（排查关键点 2）**
   - 查测试态下 vsync 所在线程 `gwsi_vsync` 的优先级：默认 **priority 0 / policy 0（SCHED_NORMAL，nice 0，PRI 19）**。
   - 用 `chrt -r -p 99 <gwsi_vsync TID>`（等效 debug 补丁 2015159/2098810，设成 **priority 99 / SCHED_RR**）拉高优先级后，**测试通过**。
   - 证明确实是**线程优先级 / CPU 调度问题**：默认优先级下 gwsi_vsync 被其他线程抢占，等待被拖长、间隔超容差。

7. **定位「为什么优先级没生效」——resource manager 不纳管 standalone app（排查关键点 3）**
   - 历史线索：GWSI 里曾有把 gwsi_vsync 设为 max 的代码（补丁 1464034），后被另一补丁 1470337 移除（未说明原因）。
   - 向 app-framework/TV 侧确认（Balan / Vulapu / Prasad Iyengar）：
     - gwsi_vsync 的优先级本应由 `/etc/app-framework/resource-manager/resource-policy.conf` 配置（该文件里**确实有** gwsi_vsync 的条目：`priority=2, policy="rr"`，并被列入 `container.essential.cpu` 的 high threadslice）。
     - Resource Manager 靠**扫描 /proc 里的线程名**来套用配置：对前台 LCM 应用有效（真机 homelauncher 的 gwsi_vsync 能拿到实时优先级 PRI 42），但 **`gwsi-test-vsync` 是 sideload 的独立测试程序，不在 resource manager 的管辖范围**，所以它的 gwsi_vsync 保持默认优先级。
   - 结论：**gwsi_vsync 作为 standalone 应用的线程，没能按 resource-policy.conf 的规则被提权**，这才是优先级没生效的直接原因；该行为在各设备上一致（所以 Brioche/Galileo/Madeleine 都复现）。

## 根因 (Root Cause)

- **主因 — 线程优先级 / CPU 调度（实机验证，跨设备一致）**
  - `gwsi-test-vsync` 的 `gwsi_vsync` 线程以默认优先级运行（SCHED_NORMAL / nice 0 / PRI 19）。GWSI 的 vsync 间隔是用户态 condition_variable 定时等待实现；低优先级下该线程被抢占，~16.6ms 的等待偶发被拖到 23ms，测得的 vsync 间隔超出 16667µs 容差 → 测试失败。
  - 验证：`chrt -r -p 99`（priority 99 / SCHED_RR）后稳定通过；`modetest` 直走内核 vsync 通过 → 排除内核/驱动，坐实用户态调度。Brioche/Galileo/Madeleine 三者均复现，进一步说明这是调度层的共性问题，与 SoC 无关。
- **直接成因 — 产品系统设计（已核实）**
  - 优先级本应由 `resource-policy.conf` + Resource Manager 施加；但 Resource Manager 按线程名扫 /proc 只覆盖受管的（前台/LCM）应用，**sideload 的独立测试程序不在其 scope**，于是 gwsi_vsync 保持默认优先级。
  - 叠加历史因素：`resource-policy.conf` 最初是为 TV 产品设计（MM 设备历史上走内部 vsync、VegaUI 不调用 onVsync via GWSI_VSYNC），且 GWSI 里显式设优先级的代码曾被移除（1470337）。
- **排除/干扰项**
  - 显示面板 FPS / PLL / MIPI / SSC：量的是面板输出帧率，与 vsync 信号到达不是一回事（排除，曾被带偏）。
  - 内核/驱动 vsync：modetest 通过（排除）。
  - DFR：关 DFR 无改善（排除，和 BOC-1215 不同）。
  - 平台/SoC 特有：三台设备均复现，排除「某颗 SoC 独有」的猜测。
- **触发条件**：以 standalone/sideload 方式跑 `gwsi-test-*`（如 gwsi-test-vsync），gwsi_vsync 拿不到实时优先级时触发；Brioche/Galileo/Madeleine 均复现，与 SoC 无关——正好印证根因是跨设备一致的调度/资源管理行为。
- **待确认**：
  - njjang 提的设计问题（见下）未解决。

## 解决方法 (Fix)

- **最终修复（test-scoped）**：Gerrit **2104611**（`meta-mediatek-brioche-dpk`，`vendor-drop-4.0`），标题「Raise gwsi_vsync priority when running gwsi-test app」。
  - 做法：在 GWSI 里加回调接口，允许 `gwsi-test` 在初始化时传入回调来设置 gwsi_vsync 线程优先级；**仅对 gwsi-test 应用生效，不影响其他使用场景**。
  - 配套：自动化脚本 `set_vsync_priority.sh`——在 gwsi_vsync 线程创建后抓到其 TID 并改优先级（chrt），测试即可通过（comment 33）。
- **仅 debug、不入主线的补丁**：Gerrit 2015159、2098810（gwsi, kepler/int/dev），用于验证「提优先级即通过」，commit message 明确标注 debug-only。
- **性质**：test-scoped workaround。它让测试程序自己把 vsync 线程提权，绕过「standalone app 不被 resource manager 纳管」的限制；**没有改动产品的 resource-policy / resource-manager 机制**。
- **评审遗留 open question**：njjang 指出 GWSI 把 vsync 实现成 client 侧 condition_variable 的 wait/timeout 并不妥，应绑定 display server 的真实呈现信号（pageFlip 事件或等价机制）。这属于更根本的重构，本票未做。
- 2026-03-04 关票（Resolution: 已修复）。

## 影响 (Impact)

- 把「gwsi-test-vsync 必挂」从「vsync 信号/面板有问题」澄清为「测试程序的 gwsi_vsync 线程没拿到实时优先级」，让 gwsi-test-vsync 可稳定通过。
- 暴露出一个产品级设计缺口：Resource Manager 只按线程名纳管受管应用，**sideload 的 gwsi-test-* 不在 scope**；`resource-policy.conf` 又是 TV 产品沿用过来的。三台设备均复现，说明这是面向所有 standalone 测试程序的共性缺口，不是单一平台问题。为后续「如何给独立测试程序施加线程策略」提供了明确案例。
- 量化：默认 priority 0 / PRI 19（SCHED_NORMAL）→ 提到 priority 99 / SCHED_RR 即通过；异常等待 23ms vs 期望 16.67ms。
- 待确认：njjang 提的 vsync 实现重构是否有后续；该 test-scoped 修复是否已 cherry-pick 到各出货分支。

## Lessons Learned

> 草稿，需要你根据自己的体会改写

1. 性能问题要从多个层面逐层验证，别停在第一个看起来合理的方向。本例一度被带去调面板 FPS/PLL（量的是显示输出帧率），而真正要测的是 vsync 信号到达——先把「测的到底是什么」定义清楚，能省掉大量无效调校。
2. 用「换一层就正常」逐层定位：`modetest`（停掉 weston 直走内核）通过 → 内核/驱动 vsync 没问题；`chrt` 提优先级后通过 → 问题在用户态线程调度。两个对照实验把范围从「vsync 坏了」收窄到「线程优先级没生效」。
3. 根因是系统调度（线程优先级），但**背后的成因是产品的系统设计**：优先级本该由 resource-policy.conf + Resource Manager 施加，而 Resource Manager 按线程名只纳管受管应用，sideload 的测试程序落在 scope 之外；再加上该配置本是 TV 产品沿用、历史上又移除过显式设优先级的代码。排 performance 问题要从「现象 → 机制 → 为什么机制会这样」一直追到设计层。
4. 跨设备对照能分清「平台特有缺陷」还是「系统共通行为」：本例在 Brioche/Galileo/Madeleine 上都复现，正好排除了「某颗 SoC 特有」的猜测，坐实根因是跨设备一致的调度/资源管理机制——不同设备的调度策略是一样的。
5. 修复要分清「治标的范围」：这里用 test-scoped 的方式让测试自己提权，解决了测试失败；但「vsync 该不该用 client 侧 timeout 实现」「standalone 测试程序怎么纳入资源策略」是更根本的 open question，关票时要显式记下来，别让 workaround 盖掉真问题。
